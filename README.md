# MacOS Config Watchdog

Local-first macOS configuration drift monitoring. This project is under active development; no monitoring agent is installed by cloning the repository.

Design: Ansible owns expected state and deployment; this repository owns discovery, local observation, SQLite history, and JSON interfaces. The personal Mac is the initial target.

## Current development status

PR #1 is a **development foundation**, not yet a deployed watchdog.
Supports inventory of top-level apps and Homebrew formulae/casks; local-only
SQLite changes, JSON export, and an event-driven watcher. It does **not** yet
provide stock-macOS classification, Ansible manifest reconciliation, weekly deep
collectors, or automatic deployment.

### Development commands

```sh
python3 -m pip install -e '.[test]'
python3 -m pytest -q
mac-watchdog scan
mac-watchdog health
mac-watchdog export
mac-watchdog monitor
```

`monitor` is macOS-only and observes selected application and Homebrew directories.
A launchd integration PR in the separate Ansible repository is required before
this will start automatically at login. By design, these commands do not modify
macOS configuration. Never paste local JSON exports into public GitHub issues.

See [ADRs](docs/adr/README.md) and [roadmap](docs/ROADMAP.md).
\nThe persistent monitor runs a deep scan when no successful deep scan is recorded,\nthen approximately weekly; routine scans cover apps and Homebrew every 30 minutes.\nAfter long wall-clock gaps it also schedules a reconciliation, which is not a\nplatform-guaranteed wake notification.\n
## Experimental local macOS log signals (PR #13)

The new `mac-watchdog logs` command analyzes a bounded, read-only five-minute
slice of macOS unified logs. Only five fixed fault signal categories from
`launchd`, `trustd`, `mDNSResponder`, and `configd` are eligible. It never
persists original log lines, commands, user paths or message text; only
rounded collection windows and counts are retained locally for seven days.
Use `mac-watchdog log-report` to read the last 100 grouped signal records.

The regular monitor schedules this check every five minutes. Queries can time
out, reach their byte/record cap, or lack permission; failures are not proof of
health and never become an empty successful observation. This is not a complete
security event monitor or audit log. No AI or automatic action is enabled.
Do not deploy this experimental feature until on-device NDJSON and permission
behavior are tested and the ADR is accepted.

## Experimental on-demand local AI review

`mac-watchdog ai-review` requests a **read-only advisory** from a locally running
Ollama `qwen3:8b` model at fixed loopback address `127.0.0.1:11434`. It uses
only counts of whitelisted log signals and inventory change categories from the
last 24 hours. No resource names, IDs, log lines, paths or private config are sent.
The model selects an observed focus category and confidence only; severity,
explanations and non-executable checks are generated by trusted local rules.
The command reports log sampling status and does not claim full coverage.
Stale collection and baseline-only additions skip local inference.
It does not call Ollama if there are no recorded findings.

The command never runs automatically, modifies system settings, stores model
answers or sends anything to GitHub. The model must be installed separately;
this feature does **not** install or start Ollama. Model output is strictly
validated, may be wrong, and must never be treated as authorization to act.
Ansible's current pinned watchdog install is unchanged in this PR.

To test real Ollama without touching the live watchdog database, run
`PYTHONPATH=src python3 tests/manual_ollama_integration.py` from this repo
on a Mac with Ollama and `qwen3:8b` already installed. The script uses a
temporary private database populated only with synthetic test data.
