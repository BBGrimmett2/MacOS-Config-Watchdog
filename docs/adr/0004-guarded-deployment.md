# ADR 0004: Guarded automatic Ansible deployment and tracked rollback

- Status: Accepted (future implementation; not enabled in Phase 1)
- Date: 2026-11-17

## Context
The initial observer was read-only. A later decision added automatic application of desired-state changes when the Ansible manifest changes. That newer requirement supersedes observation-only behavior for the distinct, guarded deployment subsystem; the AI agent itself remains read-only.

## Decision
When an authenticated/trusted expected-state manifest changes, compare desired versus last successfully applied versions. Verify the associated Ansible revision, validate changed roles, run safe dry-run/check/diff, and classify risk. Apply verified low-risk changes via approved Ansible entrypoints; security-sensitive or destructive changes require explicit user approval. Never execute playbooks or shell commands generated by an LLM.

Retry only transient failures using bounded retries (up to three attempts) and exponential backoff. Do not retry validation failures or bypass required approval. On persistent failure, automatically roll back only where the role defines a verified, tested rollback strategy. Record every rollback attempt, outcome and affected resources in local state, and create a sanitized GitHub issue even when rollback succeeds. If rollback fails, raise a critical notification and freeze further automatic changes to the affected resource/revision.

Require post-apply reconciliation before marking an operation successful. Automatic issue closure still requires two consecutive complete, successful verification scans. A previous manifest or prior playbook run alone is not proof that rollback is possible.

## Consequences
Deployment requires clear trust boundaries and a rollback capability contract per role, plus lockout, idempotency and failure recovery tests. The watchdog observer must remain functional even if Ansible deployment is unavailable.
